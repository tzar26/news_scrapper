# ADR-021: Переход к единому конвейеру обработки статей (Pipeline)

Дата: 2026-11-02
Статус: план (Приватная ветка `private/trading`)

## Контекст

В текущей архитектуре (Public MVP) обработка статей разбита на три независимые фоновые задачи Celery:
1. `classify_batch` — определяет категорию (Category).
2. `extract_batch` — извлекает сущности (NER) и тональность (Sentiment).
3. `enrich_batch` — создает эмбеддинги и суммаризацию.

Каждая задача работает независимо, опрашивая Ollama. Это приводит к **дублированию логики**:
- `enrich_batch` уже содержит проверку на `market_impact` (внутри `summarizer`), которая фактически дублирует часть классификации.
- Для статей, которые не влияют на рынок (спорт, культура, происшествия), мы всё равно тратим ресурсы GPU на NER и эмбеддинги, которые не будут использованы в аналитике.

При росте базы до 27 000+ статей это становится узким местом: GPU-время тратится на обработку «мусора».

## Решение

Перейти к **единому конвейеру обработки (Pipeline)** в рамках одной Celery-задачи.

### Логика конвейера (Fast-Fail)

Для каждой статьи выполняются шаги последовательно. Если статья не проходит фильтр на текущем шаге, она помечается как `skipped`, и ресурсы на последующие шаги не тратятся.

1. **Классификация** (`classifier`): определяем категорию.
2. **Фильтр №1 (Мусор):** если категория `sports`, `culture`, `entertainment`, `incident`, `health`, `environment` — **пропускаем** (не делаем NER, Impact, Embedding).
3. **Market Impact** (`market_impact`): оцениваем влияние на рынок.
4. **Фильтр №2 (Низкое влияние):** если `importance = low` — **пропускаем**.
5. **Извлечение сущностей** (`extractor`): NER + Sentiment.
6. **Суммаризация** (`summarizer`): делаем краткое резюме (только для важных статей).
7. **Эмбеддинг** (`embed`): создаем вектор от резюме (или от обрезанного текста).

### Ключевые изменения в коде

- Создать `tasks/pipeline.py` с единой задачей `process_batch`.
- Добавить в `ArticleRepository` метод `get_unprocessed` (статьи, у которых нет категории или эмбеддинга) и `save_all` (атомарное сохранение всех полей).
- Удалить отдельные задачи `classify_batch`, `extract_batch`, `enrich_batch` (или оставить как fallback для ручного запуска).

## Обоснование

1. **Экономия ресурсов:** Исключаем обработку 60–70% новостей (спорт, культура, происшествия), которые не влияют на рынок. Это снижает нагрузку на GPU и ускоряет обработку важных статей.
2. **Целостность данных:** Все поля (`category`, `market_impact`, `entities`, `sentiment`, `summary_text`, `embedding`) заполняются атомарно в одном месте. Это исключает ситуации, когда у статьи есть эмбеддинг, но нет категории (или наоборот).
3. **Упрощение поддержки:** Один конвейер легче отлаживать, чем три независимые задачи, которые конкурируют за ресурсы.

## Альтернативы

1. **Оставить три задачи, но добавить флаг `is_important` в БД.**
   - *Отвергнуто:* всё равно нужно три раза опрашивать Ollama для важных статей (дублирование логики остается).
2. **Сделать один гигантский промпт для Qwen (Classify + Impact + NER + Summary).**
   - *Отвергнуто:* 14B модель начнет путаться в формате JSON и галлюцинировать. Лучше делать цепочку вызовов с валидацией на каждом шаге.
3. **Использовать более мощную модель (Qwen 32B).**
   - *Отвергнуто:* не решает проблему дублирования и не экономит ресурсы.

## Последствия

- В публичном MVP (ветка `main`) остаются три задачи (как было), но в документации появляется план перехода.
- В приватной ветке (`private/trading`) реализуется конвейер, что ускоряет сбор данных для ML-модели.
