# Решение: три уровня моделей — domain, ORM, API-схемы

Дата: 2026-10-08
Статус: принято

## Контекст

Понятие «новость» представлено в проекте трижды:
- `domain/models.py::RawNewsItem` (Pydantic) — что приходит из источника.
- `db/models/article.py::Article` (SQLAlchemy ORM) — как хранится в БД.
- `api/schemas/article.py::ArticleResponse` (Pydantic) — что отдаём наружу.

Возникает соблазн объединить их: «зачем три класса для одного понятия?»

## Решение

Оставляем три уровня раздельно. Каждый слой эволюционирует независимо.

## Обоснование

### RawNewsItem ≠ Article
- RawNewsItem — до сохранения, есть только поля из RSS.
- Article — после сохранения, добавляются id, content_hash, created_at.
- Если объединить — домен начнёт зависеть от SQLAlchemy, сломается
  ADR-001 (изоляция domain от фреймворков).

### Article ≠ ArticleResponse
- Article — ORM с внутренними полями (content_hash, created_at).
- ArticleResponse — стабильный контракт для клиента. Клиенту не нужен
  content_hash, не нужен огромный text в списочном ответе.
- ORM-объект привязан к сессии. После закрытия сессии доступ к атрибутам
  даёт ошибку. Отдавать ORM наружу нельзя.
- Pydantic-схема генерирует OpenAPI. ORM — нет.

### Что даёт разделение
- Изменение схемы БД не ломает API (добавили колонку — не добавили в схему).
- Изменение API не требует изменения БД.
- Тесты каждого слоя изолированы.

## Альтернативы

1. **Одна модель на всё.** Отвергнуто: домен сцеплен с SQLAlchemy,
   нарушение ADR-001, ORM-объекты в ответах API.
2. **ORM + Pydantic-схема, без domain.** Отвергнуто: домен должен уметь
   жить без БД (тесты, парсеры, будущие агенты).
3. **Domain + Pydantic-схема, ORM без схемы.** Отвергнуто: ORM-объекты
   в ответах — прямая дорога к багам с detached instances.

## Последствия

- Маппинг между слоями явный: `ArticleResponse.model_validate(article)`.
- При добавлении поля в БД нужно подумать: нужно ли оно в API-схеме.
- Дублирование типов (например, `country: str` в трёх местах) —
  осознанная цена за развязку слоёв.
