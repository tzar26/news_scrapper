# ADR-007: RAG-архитектура — pgvector, nomic-embed-text, cross-source evidence

Дата: 2026-10-09
Статус: принято

## Контекст

Нужен семантический поиск по собранным статьям + генерация ответов
с цитированием. Данные — новости на русском и английском, объём
пока несколько сотен статей, но архитектура должна выдерживать рост.

Дополнительное требование: сохранять перепечатки (cross-source
evidence) — если Reuters, NPR и Kommersant пишут об одном событии,
это не мусор, а доказательная база для ответа.

## Решения

### 1. Хранилище векторов: pgvector в PostgreSQL 17

Не Qdrant/Weaviate/Pinecone.

Плюсы:
- Одна БД, не надо держать отдельный сервис.
- Транзакции, JOIN'ы с метаданными (`articles`).
- Уже поднят (Docker, порт 5434, pgvector 0.8.7).
- Достаточно для объёмов до ~1 млн векторов.

Когда пересмотреть: если понадобятся шардирование, GPU-индексация
или фильтры по векторам в реальном времени на десятках миллионов.

### 2. Модель эмбеддингов: bge-m3 (1024d) через Ollama

Локальный инференс, без облачных API (санкционные ограничения
проекта).

Плюсы:
- 1024 размерность — баланс качества и памяти.
- Мультиязычная, лучше на русском, длинный контекст (8192).
- Миграция сейчас дешевле: эмбеддингов нет, пересчёт не нужен.
Цена: модель больше (1.2 ГБ), эмбеддинг медленнее, размерность 1024.

### 3. Хранение эмбеддинга: `articles.embedding Vector(1024)`, nullable

**Вариант A (выбран).** Поле в той же таблице, что и статья.

Плюсы:
- Простой SELECT без JOIN.
- Меньше кода на старте.
- Один эмбеддинг на запись.

Минусы:
- Перепечатки (одинаковый `content_hash`, разные URL) хранят
  идентичные вектора — дублирование памяти.
- При смене модели эмбеддингов — пересчёт для каждой записи,
  включая перепечатки.

Обоснование выбора сейчас: ~700 статей, перепечаток мало,
дублирование незначительно. Простота важнее.

### 4. План миграции на вариант B (отдельная таблица)

**Когда пора:**
- Статей >100k, или
- Перепечатки начинают доминировать (>30% записей), или
- Смена модели эмбеддингов становится реально дорогой.

**Целевая схема:**
```sql
CREATE TABLE article_embeddings (
    content_hash VARCHAR(64) PRIMARY KEY,
    embedding Vector(1024) NOT NULL,
    model VARCHAR(64) NOT NULL,       -- 'nomic-embed-text'
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

## Известные ограничения nomic-embed-text

При smoke-тесте на русских новостных фразах:
- близкие по смыслу: cosine ~0.85–0.9
- далёкие: cosine ~0.6–0.7

Разрыв меньше, чем на английском (~0.3). Причины:
- модель обучена преимущественно на английском;
- все фразы в одном новостном домене.

**Практические следствия:**
- Не использовать абсолютный порог cosine для отсечения.
- Брать top-K по относительной близости (top-5, top-10).
- Возможно, потребуется reranking раньше, чем планировалось.
- Кандидат на замену: `bge-m3` (1024d) — мультиязычная, лучше
  на русском. Миграция: изменение размерности колонки + пересчёт
  всех эмбеддингов. Делать при плохом recall@5.

## Эмпирические результаты (2026-10-09)

**Smoke-тест bge-m3** на русских новостных фразах:
- близкие по смыслу: cosine ~0.85
- далёкие: cosine ~0.52
- разрыв: 0.33

**Sanity-check retrieval** (запрос «ключевая ставка ЦБ», топ-5
по cosine distance на 663 статьях):
- все 5 попаданий по теме (ЦБ, МВФ, ставки, Сбер)
- дистанции: 0.535–0.569

**Сравнение с nomic-embed-text** (до миграции):
- разрыв close/different был 0.191 vs 0.326 сейчас.
- Миграция на bge-m3 дала качественный сдвиг.

**Вывод:** модель оправдала выбор, retrieval работает.
Дальнейшие улучшения (hybrid search, reranking) — по мере
необходимости, при появлении сигнала плохого recall.
