# Решение: dispose async engine pool после каждой Celery-задачи

Дата: 2026-10-08
Статус: принято

## Контекст

Celery-воркер работает с синхронными задачами. Наши источники и БД
используют async SQLAlchemy. Стандартный паттерн — обернуть async-логику
в asyncio.run() внутри sync-задачи.

Проблема: asyncio.run() создаёт новый event loop при каждом вызове и
закрывает его после завершения. SQLAlchemy engine держит пул соединений,
привязанных к создавшему их loop'у. На второй задаче пул возвращает
«мёртвые» соединения, что даёт RuntimeError: Event loop is closed.

## Решение

После каждой задачи вызывать `await engine.dispose()` внутри того же
asyncio.run(). Это закрывает все соединения пула до закрытия loop'а.
Следующая задача создаёт свежие соединения на новом loop'е.

Реализовано через обёртку `_scrape_and_dispose()` в `tasks/scraping.py`.

## Альтернативы

1. **Persistent event loop на процесс воркера.** Отвергнуто: сложнее,
   выигрыш заметен только при высокой частоте задач. У нас — раз в час.
2. **NullPool для engine.** Отвергнуто: теряем пулирование и для FastAPI
   тоже (в перспективе — общий engine).
3. **Отдельный engine для Celery с NullPool.** Отвергнуто: дублирование
   конфигурации, легче забыть синхронизировать при изменениях.

## Последствия

- Каждая задача открывает свежие соединения. Накладные расходы малы:
  ~3–5 соединений на задачу, раз в час.
- FastAPI (в перспективе) продолжит использовать пул — dispose в Celery
  процесс затрагивает только свой engine (процессы разные).
- Если появится много Celery-задач подряд — вернуться к persistent loop.
