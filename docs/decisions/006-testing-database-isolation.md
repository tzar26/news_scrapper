# Решение: тесты API работают на dev-БД (временное), изоляция — техдолг

Дата: 2026-10-09
Статус: принято, временное

## Контекст

`tests/api/test_endpoints.py` бьют по реальной БД `pet_news` — той же,
что используют uvicorn и Celery. Фикстура `client` создаёт `AsyncClient`
с `ASGITransport`, но не подменяет engine и не изолирует данные.

Плюсы текущего подхода:
- Быстрая итерация: не надо поднимать тестовую БД.
- Данные «свежие» — сразу после прогона скрапера.
- Все тесты read-only, побочных эффектов на dev-данные нет.

Минусы:
- Тесты зависят от содержимого БД. Если в `pet_news` 0 статей —
  `test_list_articles_filter_by_country` упадёт.
- Параллельный прогон тестов и Celery-задачи может давать флаки.
- Нельзя запустить в CI без provision PostgreSQL.
- Загрязняет dev-БД, если появятся write-тесты (сейчас только read).

## Решение

Оставляем как есть на этапе MVP. Изоляция тестовой БД — **техдолг**,
фиксируется этим ADR и будет закрыт, когда:
1. Появятся write-тесты (сейчас только read).
2. Или при настройке CI (GitHub Actions) — там всё равно provision
   Postgres.

## Рассмотренные альтернативы изоляции

### A. Отдельная схема в той же БД (PostgreSQL schema)

PostgreSQL поддерживает схемы — пространства имён внутри одной БД.
Можно создать `test_<uuid>`, выставить `search_path` и получить
изоляцию.

Плюсы:
- Не нужны права на `CREATE DATABASE`.
- Расширения (`pgvector`) остаются доступны — они на уровне БД.
- Одна физическая БД, меньше конфигурации в Docker.

Минусы:
- С SQLAlchemy нужно выставлять `search_path` через `connect_args`
  или событие `connect`.
- С Alembic сложнее: требуется `version_table_schema`,
  `include_schemas=True`, аккуратный `env.py`.
- Меньше документации/примеров, чем для отдельной БД.

Отвергнуто из-за сложности с Alembic на текущем этапе.

### B. Отдельная тестовая БД `pet_news_test`

Простейший вариант: своя БД на том же сервере PostgreSQL.

Плюсы:
- Полная изоляция.
- С Alembic тривиально: другой `DATABASE_URL` — прогнали
  `alembic upgrade head` — работаем.
- Легко пересоздать: `DROP DATABASE ... ; CREATE DATABASE ...`.
- Много примеров и готовых рецептов.

Минусы:
- Нужны права на `CREATE DATABASE` (у нас есть — Docker, суперюзер).
- Чуть больше кода в фикстурах (`conftest.py` создаёт/удаляет БД).

**Выбран как следующий шаг.** Реализуем, когда дойдём до CI или
write-тестов. Схема внедрения:
- Session-scoped фикстура в `tests/conftest.py`:
  - подключается к служебной БД `postgres`,
  - создаёт `pet_news_test`, если нет,
  - прогоняет `alembic upgrade head` с тестовым URL,
  - возвращает DSN для тестового engine.
- Тестовый engine изолирован от dev-engine.
- После прогона — TRUNCATE между тестами, DROP в конце сессии
  (опционально — оставить для скорости повторного запуска).

### C. Testcontainers

`testcontainers-python` поднимает `pgvector/pgvector:pg17` в Docker
на время теста, ждёт `healthy`, отдаёт DSN, гасит после.

Плюсы:
- Абсолютная изоляция.
- Не зависит от локальной БД.
- Идеален для CI.
- Версия PG фиксирована в коде — воспроизводимо у любого разработчика.

Минусы:
- Требует Docker в окружении (есть не везде — например, внутри
  некоторых CI-раннеров).
- Запускается медленнее (10–30 секунд на подъём контейнера).
- Ещё одна зависимость в dev-окружении.

**Выбран как цель для CI**, после варианта B. Локально может
использоваться опционально — флаг `USE_TESTCONTAINERS=1`.

## Последствия

- **Сейчас:** тесты бьют по `pet_news`. Не запускать их одновременно
  со скрапером или Celery-задачей в один момент времени.
- **Когда дойдём до CI:** переезд на вариант B (отдельная БД),
  затем C (testcontainers).
- **Индикатор для ревьюера:** этот ADR показывает, что проблема
  изоляции тестов осознана и отложена намеренно, а не проигнорирована.

## Признаки, что пора закрывать техдолг

- Появился первый write-тест.
- Настраивается CI.
- Прогон тестов и скрапера параллельно начал давать флаки.
- Кто-то (включая автора через полгода) пытается понять, почему
  тесты не запускаются на пустой БД.
