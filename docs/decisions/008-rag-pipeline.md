# ADR-008: RAG-пайплайн — retriever, дедупликация, fallback

Дата: 2026-10-12
Статус: принято

## Контекст

Эмбеддинги статей посчитаны (bge-m3, 1024d), HNSW-индекс создан.
Нужен retrieval + генерация ответов с цитированием источников.

Специфика проекта:
- Перепечатки сохранены (cross-source evidence), нужно дедуплицировать
  на этапе retrieval, не ingest.
- Статьи короткие (500–3000 знаков) — один chunk на статью.
- Локальная LLM через Ollama, никаких облачных API.
- LangChain разрешён только в `rag/chains.py` и `agents/`.

## Решения

### 1. Retrieval — SQL через pgvector, без LangChain

`rag/retriever.py::search()` — чистая async-функция:
- embed запроса через OllamaClient,
- SELECT через pgvector (оператор `<=>`),
- фильтры по метаданным (country, category, published_at),
- дедупликация по `content_hash`: top-K **уникальных историй**,
  для каждой — список связанных article_id и url.

LangChain здесь не нужен — это простой SQL. Изоляция по ADR-001.

### 2. Дедупликация на retrieval

pgvector возвращает top-N по близости (N = top_k * 3, с запасом на дубли).
Затем в Python:
- группируем по `content_hash`,
- оставляем одну «представительскую» статью на группу (самую близкую),
- собираем все связанные URL.

Результат: `SearchResult` — dataclass с полями:
- `representative_id`, `representative_url`, `title`, `text`, `distance`,
- `content_hash`,
- `related: list[tuple[int, str]]` — (id, url) перепечаток.

### 3. Промпт — LangChain, но с явными правилами

`rag/prompts.py` — системный промпт:
- Требует цитирования `[article_id]` для каждого утверждения.
- Fallback: если в контексте нет ответа — «не найдено в базе».
- Запрет на использование собственных знаний вне контекста.

`rag/chains.py` — LangChain chain:
- `ChatOllama(model='qwen2.5-coder:14b-16k')`,
- prompt template,
- `|` композиция.

LangChain оправдан: композиция, шаблоны, переиспользование.

### 4. API — `POST /ask`

Request:
```json
{"question": "что влияет на рынок нефти за неделю?", "top_k": 5}
```
Response:
```json
{
  "answer": "...",
  "sources": [
    {"id": 123, "url": "...", "title": "..."},
    {"id": 456, "url": "...", "title": "..."}
  ]
}
```

## Эмпирические результаты (2026-10-12)

Smoke-тест retriever на 663 статьях, top-5:

- «ключевая ставка ЦБ» → 5/5 релевантных, distance 0.535–0.569.
- «нефть добыча ОПЕК» → 5/5 релевантных, distance 0.448–0.510.
- «автомобильный рынок Китая» → релевантность низкая: модель
  вытягивает всё про Китай, теряя «авторынок».

**Выводы:**
1. Retriever работает на простых тематических запросах.
2. Абсолютное значение distance зависит от темы — универсальный
   порог не работает, только относительный top-K.
3. Составные запросы (два концепта) — слабое место чистого
   vector search. Кандидат на hybrid search или query decomposition.
4. Запрос «автомобильный рынок Китая» не находит релевантного,
   потому что в базе нет статей на эту тему. Retriever не может
   найти то, чего нет — это ограничение данных, а не модели.

**Признаки, что пора улучшать:**
- Низкий recall@5 на составных запросах → query decomposition.
- Точные термины (артикулы, имена) не находятся → hybrid search.

## Эмпирические результаты — уточнение (2026-10-12)

Детальный анализ показал, что retrieval хуже, чем следовало
из первоначального smoke-теста:

- «ключевая ставка» → 1/3 релевантных (остальное — совпадения
  по отдельным словам «ставка» / «ЦБ»).
- «Что нового с ключевой ставкой?» → 0/3.
- «ключевая ставка ЦБ» → 0/3 по смыслу (совпадения по словам).

**Причины:**
1. Мало данных (663 статьи на 3 источниках) — модель работает
   в узком конусе, всё кажется «похожим».
2. Чистый vector search не различает точные термины.
3. В базе нет статей именно про ключевую ставку ЦБ РФ.

**Вывод:** качество retrieval ограничено данными и архитектурой
(чистый vector). MVP API можно строить, но улучшение retrieval —
следующий приоритет.

**План улучшений (по приоритету):**
1. Расширение источников (тематические финансовые фиды).
2. Hybrid search: BM25 (pg_trgm / tsvector) + vector, объединение
   через RRF.
3. Reranking (cross-encoder) на топ-50 → топ-5.
4. Query decomposition для составных запросов.

**Что НЕ делаем сейчас:** ни одно из улучшений — до завершения
API-слоя (/ask). Сначала MVP, потом качество.

## Эмпирические результаты — после расширения источников (2026-10-13)

База: 1193 статьи, 7 источников (Kommersant, RBC, TASS, NPR, WSJ, Xinhua, Global Times).

**Улучшилось:**
- «ключевая ставка ЦБ»: топ 0.444 с релевантной статьёй (было 0.535, мусор).
  3/5 попаданий в тему (было 0/5). Вклад RBC.
- «нефть ОПЕК»: 5/5, дистанции улучшились (топ 0.444 vs 0.448).

**Осталось проблемным:**
- «автопром Китая»: 1/5 (было 0/5). Причина — нет отраслевых
  китайских источников, общие фиды не закрывают тему.
- «золото»: 1/5 явно релевантных. Чистый vector search не
  различает «золото» (металл) и «золото» (медаль), даёт мусор
  (пустые статьи, ВЦИОМ про деньги).

**Вывод:**
1. Расширение источников дало качественный сдвиг на финансовых
   темах (+3 попадания из 5 в «ставке»).
2. Достигнут предел чистого vector search: мусор в выдаче
   (однословные совпадения, пустые статьи).
3. Обнаружены пустые статьи (например, id=1649) — нужен фильтр
   на ingest: min_length=100 для text.

**Следующие приоритеты:**
1. Фильтр на ingest — не сохранять статьи с коротким text.
2. Hybrid search (BM25 + vector + RRF) — точные термины.
3. Reranking — precision@5, отсечение мусора.
4. Отраслевые китайские источники (позже).

## Финальная диагностика перед hybrid (2026-10-13)

Детальный анализ top-5 по четырём запросам на 1191 статье:

| Запрос | Релевантных | Причина |
|---|---|---|
| ключевая ставка ЦБ | 1/5 | «ЦБ» — общий термин, статьи разные |
| автопром Китая | 1/5 | Составной концепт + мало данных |
| золото | 1/5 | Омонимия: металл vs медаль |
| нефть ОПЕК | 5/5 | Узкий домен, буквальное совпадение терминов |

**Ключевое наблюдение:** «нефть ОПЕК» работает не потому
что vector search «умный», а потому что термины («Brent»,
«$X за баррель», «ОПЕК») буквально повторяются. BM25 дал бы
тот же результат.

**Три класса проблем, требующих разных решений:**
1. Общие термины в разных контекстах («ЦБ») → **BM25 по фразе**.
2. Составные запросы + пробелы в данных → **query decomposition + источники**.
3. Омонимия («золото») → **reranking (cross-encoder)**.

**Вывод:** hybrid search (BM25 + vector + RRF) — следующий шаг.
Reranking — после оценки hybrid.

## Эмпирические результаты после расширения до 14 источников (2026-10-13)

База: ~1680 статей, 14 источников.

**Закрытые просадки:**
- «автопром Китая»: 0/5 → 3/5. Появились CNBC, WSJ,
  GlobalTimes с релевантными материалами.
- «ключевая ставка ЦБ»: топ-2 релевантны (было 1/5).
  Новые источники (Interfax, Prime) дали материал про
  абсорбцию ликвидности.
- «нефть ОПЕК»: топ-5 стал разнообразнее — пять разных
  аспектов темы (добыча, цены, экспорт, ОПЕК+, аналитика).

**Осталось проблемным:**
- «золото»: омонимия («металл» vs «медаль»). Добавился
  один релевантный аналитический материал (WSJ/CNBC),
  но мусор остаётся. Решение — reranking или уточнение
  запроса.

**Главный вывод:** на малых объёмах данных расширение
источников даёт больше, чем оптимизация алгоритма.
Hybrid search + 14 источников = рабочая конфигурация.

## Кейсы для проверки reranking (2026-10-15)

Запросы, где baseline-метрики плохие:

1. **«экспорт российского газа»** — recall@5 = 0.0.
   Статьи по теме в базе есть, но retrieval не выдаёт их в топ.
   Гипотеза: bge-m3 усредняет семантику «газа» (добыча,
   экспорт, поставки сливаются). BM25 требует AND всех трёх слов.
   Проверка после reranking: ожидаем рост recall@5.

2. **«нефть ОПЕК»** — recall@5 = 0.25 (при precision@5 = 1.0).
   Retrieval выдаёт точные, но мало (только 1 из 4+ релевантных).
   Гипотеза: BM25 AND-логика режет широкий запрос.

3. **«санкции против России»** — recall@5 = 0.31.
   Проверить: дело в данных или retrieval.

4. **«рынок акций США»** — 6 релевантных выпало из top-20
   после расширения корпуса. Признак перегрузки темы.
