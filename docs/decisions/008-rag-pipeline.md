# ADR-008: RAG-пайплайн — retriever, дедупликация, fallback

Дата: 2026-10-12
Статус: принято

## Контекст

Эмбеддинги статей посчитаны (bge-m3, 1024d), HNSW-индекс создан.
Нужен retrieval + генерация ответов с цитированием источников.

Специфика проекта:
- Перепечатки сохранены (cross-source evidence), нужно дедуплицировать
  на этапе retrieval, не ingest.
- Статьи короткие (500–3000 знаков) — один chunk на статью.
- Локальная LLM через Ollama, никаких облачных API.
- LangChain разрешён только в `rag/chains.py` и `agents/`.

## Решения

### 1. Retrieval — SQL через pgvector, без LangChain

`rag/retriever.py::search()` — чистая async-функция:
- embed запроса через OllamaClient,
- SELECT через pgvector (оператор `<=>`),
- фильтры по метаданным (country, category, published_at),
- дедупликация по `content_hash`: top-K **уникальных историй**,
  для каждой — список связанных article_id и url.

LangChain здесь не нужен — это простой SQL. Изоляция по ADR-001.

### 2. Дедупликация на retrieval

pgvector возвращает top-N по близости (N = top_k * 3, с запасом на дубли).
Затем в Python:
- группируем по `content_hash`,
- оставляем одну «представительскую» статью на группу (самую близкую),
- собираем все связанные URL.

Результат: `SearchResult` — dataclass с полями:
- `representative_id`, `representative_url`, `title`, `text`, `distance`,
- `content_hash`,
- `related: list[tuple[int, str]]` — (id, url) перепечаток.

### 3. Промпт — LangChain, но с явными правилами

`rag/prompts.py` — системный промпт:
- Требует цитирования `[article_id]` для каждого утверждения.
- Fallback: если в контексте нет ответа — «не найдено в базе».
- Запрет на использование собственных знаний вне контекста.

`rag/chains.py` — LangChain chain:
- `ChatOllama(model='qwen2.5-coder:14b-16k')`,
- prompt template,
- `|` композиция.

LangChain оправдан: композиция, шаблоны, переиспользование.

### 4. API — `POST /ask`

Request:
```json
{"question": "что влияет на рынок нефти за неделю?", "top_k": 5}
```
Response:
```json
{
  "answer": "...",
  "sources": [
    {"id": 123, "url": "...", "title": "..."},
    {"id": 456, "url": "...", "title": "..."}
  ]
}
```

## Эмпирические результаты (2026-10-12)

Smoke-тест retriever на 663 статьях, top-5:

- «ключевая ставка ЦБ» → 5/5 релевантных, distance 0.535–0.569.
- «нефть добыча ОПЕК» → 5/5 релевантных, distance 0.448–0.510.
- «автомобильный рынок Китая» → релевантность низкая: модель
  вытягивает всё про Китай, теряя «авторынок».

**Выводы:**
1. Retriever работает на простых тематических запросах.
2. Абсолютное значение distance зависит от темы — универсальный
   порог не работает, только относительный top-K.
3. Составные запросы (два концепта) — слабое место чистого
   vector search. Кандидат на hybrid search или query decomposition.
4. Запрос «автомобильный рынок Китая» не находит релевантного,
   потому что в базе нет статей на эту тему. Retriever не может
   найти то, чего нет — это ограничение данных, а не модели.

**Признаки, что пора улучшать:**
- Низкий recall@5 на составных запросах → query decomposition.
- Точные термины (артикулы, имена) не находятся → hybrid search.

## Эмпирические результаты — уточнение (2026-10-12)

Детальный анализ показал, что retrieval хуже, чем следовало
из первоначального smoke-теста:

- «ключевая ставка» → 1/3 релевантных (остальное — совпадения
  по отдельным словам «ставка» / «ЦБ»).
- «Что нового с ключевой ставкой?» → 0/3.
- «ключевая ставка ЦБ» → 0/3 по смыслу (совпадения по словам).

**Причины:**
1. Мало данных (663 статьи на 3 источниках) — модель работает
   в узком конусе, всё кажется «похожим».
2. Чистый vector search не различает точные термины.
3. В базе нет статей именно про ключевую ставку ЦБ РФ.

**Вывод:** качество retrieval ограничено данными и архитектурой
(чистый vector). MVP API можно строить, но улучшение retrieval —
следующий приоритет.

**План улучшений (по приоритету):**
1. Расширение источников (тематические финансовые фиды).
2. Hybrid search: BM25 (pg_trgm / tsvector) + vector, объединение
   через RRF.
3. Reranking (cross-encoder) на топ-50 → топ-5.
4. Query decomposition для составных запросов.

**Что НЕ делаем сейчас:** ни одно из улучшений — до завершения
API-слоя (/ask). Сначала MVP, потом качество.
