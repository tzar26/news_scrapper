# ADR-029: История сигналов для ретроспективы (Track Record)

Дата: 2026-11-12
Статус: внедрено (Приватная ветка `private/trading`)

## Контекст

Для оценки качества работы ML-модели и презентации проекта (инвесторам, рекрутерам) недостаточно Accuracy на тестовой выборке. Нужна **реальная статистика**: сколько сигналов было сгенерировано, сколько из них сбылось.

Также для честной ретроспективы необходимо сохранять каждый сигнал **в момент его генерации** (а не пересчитывать задним числом), чтобы избежать look-ahead bias (использования будущих данных).

## Решение

1. Создана таблица `signals_history` (модель `SignalHistory`), которая хранит:
   - `ticker`, `signal` (BUY/SELL/NEUTRAL), `strength` (strong/weak/neutral).
   - `confidence` (вероятность).
   - `reason` (объяснение, включая Sanity Check).
   - `model_version` (версия модели, например, `v20261112_1253`).
   - `price_at_generation` (цена на момент генерации — берется из локальных свечей `data/moex_candles/`).
   - `created_at` (время генерации).
   - `price_after_3d`, `is_correct`, `evaluated_at` (заполняются позже).

2. Запись в историю происходит в `api/routes/signal.py` **только при первой генерации сигнала** (при повторных запросах из кеша запись не дублируется).

3. **План оценки:** Celery-задача (раз в день) будет брать сигналы, которым уже исполнилось 3 дня (по `created_at`), запрашивать цену через 3 дня (из локальных свечей или API MOEX), сравнивать с `price_at_generation` и заполнять `is_correct` (True/False).

## Последствия

- Мы собираем данные для Track Record. Через 1–2 недели сможем показать: *«Из 50 сигналов BUY, 60% сбылись»*.
- Требуется мониторинг объёма таблицы `signals_history` (чтобы не росла бесконечно). В будущем можно добавить очистку старых записей.
- Кеширование сигналов (Redis) снижает нагрузку на API при повторных запросах и предотвращает дублирование записей в истории.

## Текущий статус (ноябрь 2026)

- Сгенерировано 14 сигналов (SBER, GAZP, LKOH, YDEX, VTBR, GMKN, ROSN, TATN, NVTK, MTSS, MGNT, OZON, VKCO, ALRS).
