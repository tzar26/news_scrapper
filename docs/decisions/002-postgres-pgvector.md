# Решение: PostgreSQL + pgvector как хранилище

Дата: 2026-09-29
Статус: принято

## Контекст

Проекту нужны:
1. Реляционное хранилище для статей, источников, сигналов.
2. Векторное хранилище для эмбеддингов (RAG на этапе 3+).

Требования проекта: self-hosted, устойчивость к санкциям,
минимум внешних сервисов, open-source стек.

## Решение

Используем **PostgreSQL 17** с расширением **pgvector** для обеих задач.

- Реляционные данные — обычные таблицы.
- Векторы — колонка типа `vector(N)` в тех же таблицах.
- Поиск по векторам — операторы pgvector (`<->`, `<#>`).
- Миграции — Alembic.
- Async-доступ — asyncpg + SQLAlchemy 2.0.

## Обоснование

### Почему не отдельная векторная БД (Qdrant, Weaviate, Pinecone)

- **Дополнительный сервис.** Ещё один контейнер, ещё один DSN,
  ещё одна точка отказа. Для пет-проекта — избыточно.
- **Дублирование данных.** Метаданные статьи лежат в PostgreSQL,
  вектор — в Qdrant. Синхронизация, транзакции, консистентность —
  всё становится сложнее.
- **Pinecone — облачный SaaS.** Санкционные риски, вендор-лок.
  Отвергнуто по ADR-001.
- **Qdrant/Weaviate self-hosted** — можно, но зачем, если pgvector
  закрывает задачу до ~1 млн векторов.

### Почему не SQLite (как было в первом README)

- Нет pgvector (или очень ограниченный).
- Плохо с конкурентной записью (Celery + API одновременно).
- Не тянет production-нагрузку.
- PostgreSQL всё равно нужен в Docker — так почему не использовать
  его для всего.

### Почему PostgreSQL 17

- Актуальная поддерживаемая версия (PG 12, которая была у меня
  изначально, — EOL).
- pgvector 0.8.7 собран под неё в официальном образе
  `pgvector/pgvector:pg17`.
- HNSW-индексы, параллельные запросы, партиционирование — всё
  доступно.

## Альтернативы

1. **SQLite + faiss (файловый индекс).** Отвергнуто: нет транзакций,
   сложно с инкрементальным обновлением, не для многопоточного доступа.
2. **PostgreSQL + Qdrant.** Отвергнуто: два сервиса ради задачи,
   которую закрывает один.
3. **MongoDB + Atlas Vector Search.** Отвергнуто: облачный SaaS,
   санкционные риски.
4. **ChromaDB (embedded).** Отвергнуто: не для продакшна, слабая
   поддержка async, ограниченные фильтры.

## Последствия

- Один сервис вместо двух — проще разработка и деплой.
- Транзакции: вставка статьи и её эмбеддинга — атомарно
  (в перспективе).
- Alembic миграции покрывают и векторные поля.
- Потолок: ~1–10 млн векторов на одной ноде PostgreSQL.
  Для проекта с новостями — с запасом.
- Когда упрёмся: при 10+ млн векторов или жёстких требованиях
  по латентности (<10 мс на запрос) — рассмотреть выделенную
  векторную БД. Но это не наш сценарий на годы вперёд.
